# Objective

Hash API keys before storage (plaintext keys in DB = full account takeover on DB compromise) and add path canonicalization to the share route.

# Implementation Plan

1. Fix `server/db.py` API key storage:
   - On key creation: generate UUID, hash with `hashlib.sha256`, store hash
   - Return raw key to user ONCE (on creation response)
   - On lookup (`get_player_by_api_key`): hash incoming key, compare hashes
   - Migration: existing plaintext keys need migration path
     - Option A: hash all existing keys on startup (one-time migration)
     - Option B: dual-mode — try hash lookup first, fall back to plaintext, migrate on match

2. Fix `server/routes/share.py` (lines 24-35):
   - Add `path.resolve().is_relative_to(results_dir.resolve())` check before file read
   - Match the same pattern used in `server/routes/match.py`

3. Tests in `tests/test_s49_api_keys.py`:
   - Created API key is returned as raw UUID
   - Stored key in DB is NOT the raw UUID (it's a hash)
   - Lookup by raw key succeeds (hash comparison works)
   - Lookup by wrong key fails
   - Share route rejects symlink escape attempts
   - Share route path check matches match route pattern

# Acceptance Criteria

- [x] API keys stored as SHA-256 hashes, not plaintext
- [x] Key creation returns raw key, DB stores hash
- [x] Key lookup works via hash comparison
- [x] Share route has path canonicalization check
